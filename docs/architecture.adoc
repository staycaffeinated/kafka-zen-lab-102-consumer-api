= Architecture Reference
kafka-zen-lab-102-consumer-api

This document describes the architecture of the Kafka consumer API, the rationale behind key design decisions, and the rules that enforce those decisions at build time.

== System Context

The service is one node in the kafka-zen-lab series. It sits downstream of `kafka-zen-lab-101-traffic-simulator`, which produces synthetic click-stream events onto a Kafka topic. This service consumes those events, transforms them into domain objects, and hands them to persistence.

== Architectural Style

The application combines two complementary patterns.

=== Hexagonal Architecture (Ports and Adapters)

The domain core is shielded from all framework and infrastructure concerns by a ring of ports (Java interfaces) and adapters (concrete implementations). Nothing in the domain layer imports Spring, Kafka, Jackson, or any persistence technology.

=== Clean Architecture Layers

Four concentric layers enforce a strict inward dependency rule. Each outer layer may depend on inner layers; no inner layer may reference anything from an outer layer.

[cols="1,2,3"]
|===
|Layer |Package Root |Responsibility

|Domain
|`zen.lab.consumer.domain`
|Sealed event interfaces, value-object records, shared constants. Zero framework dependencies.

|Application
|`zen.lab.consumer.application`
|Use-case interfaces (inbound ports), outbound port interfaces, application services, and exception types.

|Adapters
|`zen.lab.consumer.adapters`
|Inbound Kafka listener and REST controller; outbound in-memory event store; validation annotations.

|Infrastructure
|`zen.lab.consumer.infrastructure`
|Spring configuration beans, Jackson setup, CORS, error handler, resource-ID provider. Wires everything together.
|===

=== ArchUnit Enforcement

`ArchitectureTest` (in `src/test`) uses ArchUnit to assert the dependency rules at build time. The following rules are verified on every `./gradlew build`:

[cols="1,3"]
|===
|Rule |Assertion

|Domain isolation
|No class in `domain` depends on `application`, `adapters`, or `infrastructure`

|Application isolation
|No class in `application` depends on `adapters` or `infrastructure`

|Adapter/infrastructure separation
|Adapters do not depend on infrastructure; infrastructure does not depend on adapters

|Domain purity
|No class in `domain` imports `org.springframework` or `jakarta.persistence`

|Port contracts
|All classes in `application.port.inbound` and `application.port.outbound` are interfaces

|Controller placement
|`@RestController` classes reside in `adapters..inbound` and are suffixed `Controller`

|Advice placement
|`@ControllerAdvice` classes reside in `infrastructure.advice`

|Service placement
|`@Service` classes reside in `application.service`

|Kafka listener placement
|Methods annotated `@KafkaListener` are declared in classes inside `adapters`

|No field injection
|`@Autowired` on fields is prohibited throughout the codebase

|Naming: configurations
|`@Configuration` classes in `infrastructure.config` are suffixed `Configuration`

|Naming: exceptions
|All `Exception` subclasses are suffixed `Exception`
|===

=== Design Decisions

The domain types are Java records, which enforces immutability by construction. Custom `Builder` inner classes are provided on each record so that test code and future factory methods can assemble instances without relying on constructor argument position. The `ClickEvent` sealed interface restricts the permitted subtypes to exactly `ProductViewedEvent` and `ProductAddedToCartEvent`, enabling exhaustive pattern matching in `ClickEventMessageMapper.toDomain()` without a default branch.

== Inbound Kafka Adapter

=== Message Type Discrimination

Kafka delivers raw JSON bytes. Spring Kafka's `JsonDeserializer` is configured with:

* `spring.json.value.default.type` = `ClickEventMessage` (the abstract sealed base class)
* `spring.json.trusted.packages` = `zen.lab.*`

Jackson resolves the concrete subtype at deserialisation time using the `eventType` field, which is declared in `@JsonTypeInfo` on `ClickEventMessage`. The two permitted subtypes are registered via `@JsonSubTypes`.

=== Acknowledgement Mode

The listener runs with `MANUAL_IMMEDIATE` ack-mode. The consumer commits the offset only after `messageConsumerUseCase.process(...)` returns successfully. If processing raises an exception before `acknowledgment.acknowledge()` is called, the `DefaultErrorHandler` intercepts it, retries up to three times with a one-second fixed back-off, then publishes the raw bytes to the dead-letter topic.

=== Dead-Letter Queue

The `DefaultErrorHandler` bean in `KafkaConsumerConfiguration` creates an isolated producer factory (not exposed as a Spring bean) to avoid displacing Spring Boot's auto-configured `ProducerFactory<Object,Object>`. The DLQ producer serialises with `ByteArraySerializer` and uses partition `-1` to let the broker select the target partition.

== Validation Annotations

Three custom Bean Validation constraints are defined in `adapters.edge.inbound.validation`. They are intended for use on REST path variables and request body fields in future controllers.

[cols="1,2,2"]
|===
|Annotation |Validator |Rule

|`@Alphabetic`
|`AlphabeticValidator`
|All characters must satisfy `Character::isAlphabetic`. Rejects spaces, digits, and punctuation.

|`@ResourceId`
|`ResourceIdValidator`
|Exactly 27 alphanumeric characters, matching the format produced by `ResourceIdGenerator`.

|`@SearchText`
|`SearchTextValidator`
|Nullable or empty values pass. Non-empty values must not exceed 24 characters.
|===

Validation messages are externalised in `src/main/resources/ValidationMessages.properties`.

== Resource ID Generation

`ResourceIdGenerator` implements `ResourceIdSupplier` and produces 27-character alphanumeric strings using a `SecureRandom` DRBG instance. The design gives 160-bit entropy — consistent with the upper bound of the OAuth2 recommendation — and uses only URL-safe characters from the RFC 1738 alphabet.

The 27-character length constant is centralised in `ResourceIdFormat.RESOURCE_ID_LENGTH` and is referenced by both the generator and `ResourceIdValidator`, ensuring the producer and validator always agree on the expected format.

== Extending the Application

=== Adding a New Event Type

. Add the new `eventType` string constant to `Schema` if it must be referenced elsewhere.
. Create a concrete subclass of `ClickEventMessage` (annotated with `@JsonSubTypes.Type` on the base class).
. Add a new record implementing `ClickEvent` in `domain.events`.
. Add a mapping branch in `ClickEventMessageMapper.toDomain()`. The compiler will warn on the exhaustive `switch` if the new sealed subtype is not handled.
. Add or extend the use-case service as needed.

=== Replacing `InMemoryClickEventStore`

`InMemoryClickEventStore` is a development stub that logs and discards events. To persist events:

. Implement `ClickEventStore` in a new class under `adapters.edge.outbound.persistence` (or a new persistence subpackage).
. Register it as a Spring bean (e.g., `@Component`).
. Remove or qualify the stub bean to avoid ambiguity.
. Add integration tests covering the new implementation.
